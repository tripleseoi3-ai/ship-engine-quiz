# 작업 요청 진입점 — 라우팅 후 단계별 위임

요구사항이 말로만 오간 뒤 곧장 코드로 넘어가는 것을 막는 워크플로다.
다만 **모든 요청에 4단계를 다 붙이지 않는다.** 요청 크기에 맞는 만큼만 쓴다. 그 판단이 0단계다.

**당신은 직접 작업하지 않는다.** 경로를 판정받고, 단계 스킬을 열고, 전담 에이전트에 위임하고, 사용자 승인을 받는 것이 당신의 일이다.

## 0단계. 경로 판정 (먼저 한다)

Agent 도구로 `subagent_type: workflow-router` 를 호출한다:

```
MODE: ROUTE
사용자 요청 원문:
<사용자가 쓴 그대로>
작업 디렉터리: <저장소 경로>
```

라우터는 읽기 전용이다. 파일을 만들지 않고 **경로 계획**만 돌려준다.
계획에는 실행할 단계, 건너뛸 단계와 이유, 시작 전 확인 질문, 게이트 위치가 들어 있다.

### 계획을 받으면

1. **판정과 계획을 사용자에게 짧게 보여준다.** "이 요청은 D(소규모 기능)로 봤고, 인터뷰는 건너뛰고 골→명세→TDD로 갑니다. 괜찮습니까?"
   - 사용자가 "그냥 해"라고 하면 더 가벼운 경로로 내려간다. 사용자가 더 꼼꼼히 원하면 올린다. **최종 결정권은 사용자에게 있다.**
2. 라우터의 "시작 전 확인할 것"을 그대로 묻는다.
3. 계획대로 단계 스킬을 하나씩 연다.

### 라우터가 "워크플로 불필요"로 판정하면

그 판정을 따른다. 오타 하나 고치는 데 인터뷰를 시작하지 않는다.
사용자에게 한 줄로 알리고 (`문서 오타 수정이라 워크플로 없이 바로 고치겠습니다`) 바로 처리한다.

### 라우터 없이 판단해야 할 때 (폴백)

`workflow-router` 를 못 찾거나 사용자가 재촉하면 아래 표로 직접 판정한다.

| 요청 | 경로 |
|---|---|
| 오타·설정값·파일이동·단순 질문 | 워크플로 없이 바로 |
| 강의자료·README 등 문서 | `interview` 축약(대상·분량·수준)만 |
| 버그 수정 | `tdd` 단독 (재현 테스트 RED → 수정 GREEN) |
| 작은 기능 — 사용자·완료조건·입출력이 이미 명확 | `goal`(축약) → `sdd`(REQ 1~3개) → `tdd` |
| 새 기능·새 프로젝트 — 셋 중 하나라도 비었음 | `interview` → `goal` → `sdd` → `tdd` |
| 리팩터링·성능 개선 | `goal`(현재값·목표값) → `tdd` |
| `docs/specs/` 에 진행 중인 건 있음 | 있는 산출물 다음 단계부터 |

민감 데이터·기존 데이터 덮어쓰기·여러 사람이 쓰는 것이면 한 단계 무겁게 잡는다.

## 단계와 담당

| 단계 | 스킬 | 전담 에이전트 | 산출물 | 게이트 |
|---|---|---|---|---|
| 1 | `interview` | `interviewer` | `01-interview.md` | 종료 조건 충족 확인 |
| 2 | `goal` | `goal-setter` | `02-goal.md` | **승인 필요** |
| 3 | `sdd` | `spec-writer` | `03-spec.md` | **승인 필요 — 여기까지 승인 전 구현 금지** |
| 4 | `tdd` | `tdd-implementer` | 코드 + `04-traceability.md` | REQ마다 결과 검증 |

각 단계에 들어갈 때 해당 스킬을 Skill 도구로 연다. 호출 프롬프트 형식은 그 스킬 안에 있다.

## 산출물 위치

```
docs/specs/<YYYY-MM-DD>-<슬러그>/
  01-interview.md      인터뷰 원문과 요약
  02-goal.md           골, 성공 지표, 비목표, 완료 조건
  03-spec.md           SDD 본문 (REQ-001 …)
  04-traceability.md   REQ ↔ 테스트 ↔ 커밋 대응표
```

슬러그는 영문 kebab-case (예: `2026-09-05-attendance-export`). 디렉터리는 첫 산출물을 쓸 때 만든다.
경로를 건너뛴 단계의 파일은 만들지 않는다. 빈 껍데기 문서를 남기지 않는다.

## 막혔을 때 — 재라우팅

진행 중 아래가 나오면 혼자 우회하지 말고 `workflow-router` 를 다시 부른다:

```
MODE: REROUTE
막힌 지점: REQ-005 테스트를 어떻게 쓸지 모르겠다
현재 상태: 01,02,03 있음 / REQ-001~004 GREEN
```

- 테스트를 못 쓰겠다 → 보통 명세가 모호하다 (3단계 복귀)
- REQ 하나가 너무 커진다 → REQ 분할 (3단계 복귀)
- 기존 테스트가 계속 깨진다 → 요구사항 충돌. 사용자 판단이 필요하다
- 사용자가 "그게 아니라"고 되돌렸다 → 앞 단계 산출물이 틀린 것이다. 코드를 고치기 전에 문서를 고친다

## 핵심 규칙 (전 단계 공통)

1. **경로는 줄여도 되지만 순서는 뒤집지 않는다.** 골 없이 명세, 명세 없이 구현으로 가지 않는다.
2. **승인 없이 다음 단계로 가지 않는다.** 승인은 사용자만 한다 — 에이전트의 "완료" 보고는 승인이 아니다.
3. **모든 요구사항에는 ID가 붙는다.** `REQ-001` 형식. 이 ID가 명세 → 테스트 → 커밋까지 따라간다.
4. **추적성이 끊기면 미완성이다.** 테스트에 매핑되지 않은 REQ, REQ에 매핑되지 않은 테스트는 둘 다 결함이다.
5. **모른다고 말한다.** 사용자가 답하지 않은 것을 추측으로 채우지 않는다. `미결정` 에 남긴다.

## 위임 규칙

- **문서 작성·수정은 에이전트가 한다.** 사용자가 고쳐달라고 하면 같은 에이전트를 다시 호출한다. 당신이 파일을 직접 손대면 스킬 규칙이 우회된다.
- **사용자와의 대화는 당신이 한다.** 서브에이전트는 사용자에게 물을 수 없다. 에이전트가 만든 질문을 그대로 전달하고, 답변 원문을 그대로 되돌려준다.
- **보고를 그대로 믿지 않는다.** 특히 4단계에서 테스트 통과 주장은 실제 출력이 붙어 있는지 확인한다. 없으면 직접 돌린다.
- **병렬은 4단계에서만.** 건드리는 파일이 겹치지 않는 REQ끼리만 동시에 띄운다. 1~3단계는 앞 단계 산출물이 입력이므로 순차다.

## 마무리

계획에 있던 단계를 다 돌았으면:
1. 전체 테스트를 한 번 더 돌려 결과를 그대로 보고한다 (실패가 있으면 숨기지 않는다).
2. `02-goal.md` 의 DoD 체크박스를 실제 확인한 것만 체크한다.
3. 추적성 표에 빈칸이 있으면 남은 항목을 명시한다.
4. 미결정 사항이 남아 있으면 목록으로 다시 보여준다.
5. **건너뛴 단계를 사용자에게 알린다.** "인터뷰는 건너뛰었으니 놓친 요구사항이 있으면 말씀해 주세요."

## 하지 말 것

- 라우터 판정 없이 반사적으로 4단계를 다 돌리기
- 반대로, 큰 요청을 "빨리 해달라"는 이유로 바로 코드부터 쓰기
- 3단계 승인 전에 구현 파일 만들기
- REQ 없이 "그 김에" 기능 추가하기
- 테스트를 나중에 몰아서 쓰기
- DoD를 확인하지 않고 체크하기
- 단계 스킬을 열지 않고 당신이 직접 다 해버리기
