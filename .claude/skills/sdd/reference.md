# 3단계: SDD (Spec-Driven Development)

목적: 골을 **구현 가능하고 테스트 가능한 명세**로 바꾼다. 이 문서가 4단계 테스트의 원본이 된다.

## 요구사항 쓰는 법

각 요구사항은 ID를 갖고, **관찰 가능한 동작 하나만** 서술한다.

```
REQ-003  결석 3회 초과자 표시
  주체: 조교
  조건: 업로드된 출석부에 특정 학번의 결석이 4회 이상 기록된 경우
  동작: 결과 화면의 "경고" 목록에 해당 학번과 이름을 표시한다
  근거: 02-goal.md 지표 2
```

규칙:
- 한 REQ에 "그리고"가 두 번 이상 나오면 쪼갠다.
- "빠르게", "직관적으로", "안정적으로" 같은 말은 쓰지 않는다. 숫자나 관찰 가능한 사실로 바꾼다.
- 구현 방법(어떤 라이브러리, 어떤 함수)은 요구사항이 아니다. 별도 절(설계 결정)에 쓴다.
- ID는 재사용하지 않는다. 요구사항을 삭제해도 번호는 비워두고 `(철회)` 로 남긴다.

## 문서 구조

1. **개요** — 한 문단. 이게 무엇인지.
2. **용어** — 뜻이 갈릴 수 있는 단어만. (예: "결석"이 지각 2회를 포함하는가?)
3. **요구사항** — REQ-001 …. 기능 요구와 비기능 요구를 나눠 쓴다.
4. **인터페이스 / 계약** — 입력 형식, 출력 형식, 파일 경로, 명령줄 인자, 함수 시그니처.
   - 입력 예시와 출력 예시를 **실제 값으로** 하나씩 붙인다.
5. **데이터 모델** — 다루는 데이터의 필드, 타입, 필수 여부, 제약.
6. **시나리오** — Given / When / Then. 정상 흐름과 예외 흐름 모두.
7. **에러 처리** — 무엇이 잘못될 수 있고, 그때 사용자에게 무엇을 보여주는가.
8. **경계 조건** — 빈 입력, 최대 크기, 중복, 순서 뒤바뀜, 인코딩.
9. **설계 결정** — 왜 그렇게 만들었는가. 대안과 기각 이유.
10. **미결정** — 아직 못 정한 것. 누구에게 물어야 하는지까지.

## 시나리오 쓰는 법

```
S-01  중복 학번이 섞인 출석부 (REQ-005)
  Given  같은 학번이 2행에 걸쳐 들어 있는 CSV
  When   업로드한다
  Then   처리를 중단하지 않고, 해당 학번을 "확인 필요" 목록에 넣은 뒤
         나머지 행은 정상 집계한다
```

- 시나리오마다 다루는 REQ ID를 괄호에 적는다. 이게 4단계 추적성의 출발점이다.
- **예외 시나리오가 정상 시나리오보다 적으면 덜 쓴 것이다.** 보통 예외가 더 많다.

## 에러 처리 표

| 상황 | 감지 방법 | 사용자에게 보이는 것 | 시스템 동작 |
|---|---|---|---|
| CSV 인코딩이 EUC-KR | 디코딩 실패 | "파일 인코딩을 UTF-8로 저장해 주세요" | 처리 중단, 파일 변경 없음 |

"예외를 잡아서 로그만 남긴다"는 처리 방법이 아니다. 사용자가 다음에 무엇을 해야 하는지 적는다.

## 완결성 점검 (승인 전 체크)

- [ ] 모든 REQ가 `02-goal.md` 의 골 또는 지표로 되짚어진다
- [ ] 골의 모든 지표를 커버하는 REQ가 있다
- [ ] 모든 REQ에 최소 1개의 시나리오가 있다
- [ ] 각 입력마다 "잘못된 값이 들어오면?" 이 적혀 있다
- [ ] 비목표에 있는 것이 REQ로 슬쩍 들어와 있지 않다
- [ ] 미결정 항목마다 "누가 답할 수 있는지" 가 적혀 있다

## 승인 게이트

**여기까지 승인되기 전에는 구현 코드를 한 줄도 쓰지 않는다.**
사용자에게 요구사항 목록만 따로 뽑아 보여주고 빠진 것 / 필요 없는 것을 확인받는다.
