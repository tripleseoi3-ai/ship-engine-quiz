# 4단계: TDD

목적: 명세의 REQ를 하나씩 실행 가능한 테스트로 바꾸고, 그 테스트를 통과시키는 최소한의 코드를 쓴다.

## 루프

REQ 하나당 한 바퀴:

### RED — 실패하는 테스트를 먼저
1. `03-spec.md` 에서 REQ 하나와 그 시나리오를 고른다.
2. 테스트를 쓴다. 이름에 REQ ID를 넣는다: `test_req_003_결석_4회면_경고목록에_들어간다`
3. **테스트를 실행하고 실패 출력을 사용자에게 보여준다.**
   - 여기서 "실패했다"고 말만 하고 넘어가지 않는다. 실제 출력을 붙인다.
   - 실패 이유가 `ImportError` / `NameError` 뿐이면 그것도 정상적인 RED다.
   - **엉뚱한 이유로 실패하면(오타, 픽스처 누락) 고치고 다시 돌린다.** 그 상태로 GREEN에 가지 않는다.

### GREEN — 통과시키는 최소 코드
4. 이 테스트를 통과시키는 데 필요한 것만 쓴다. 다음 REQ를 미리 구현하지 않는다.
5. 테스트를 다시 돌린다. 통과 출력을 보여준다.
6. **기존 테스트가 깨졌는지 전체를 돌려 확인한다.** 새 테스트만 돌리고 끝내지 않는다.

### REFACTOR — 초록불에서만
7. 중복 제거, 이름 정리, 구조 개선. 동작은 바꾸지 않는다.
8. 리팩터 후 전체 테스트를 다시 돌린다.

### COMMIT
9. 커밋 메시지 첫 줄에 REQ ID:
   ```
   REQ-003: 결석 4회 이상이면 경고 목록에 포함
   ```
10. `04-traceability.md` 에 한 줄 추가한다.

## 절대 규칙

| 규칙 | 이유 |
|---|---|
| 실패를 눈으로 확인하기 전에 구현 코드를 쓰지 않는다 | 통과하는 걸 못 보면 그 테스트가 뭘 검사하는지 알 수 없다 |
| 테스트를 약화시켜 통과시키지 않는다 | 명세가 틀린 거라면 3단계로 돌아가 명세를 고치고 사용자 승인을 다시 받는다 |
| `assert True`, 단언 없는 테스트, 스킵 마킹으로 초록불을 만들지 않는다 | 거짓 안전이 무테스트보다 나쁘다 |
| REQ에 없는 기능을 "겸사겸사" 넣지 않는다 | 테스트도 명세도 없는 코드가 된다 |
| 테스트가 느리다고 삭제하지 않는다 | 느린 테스트는 분리하되 남긴다 |

## 무엇을 테스트할 것인가

REQ 하나당 최소:
- **정상 경로** 1개
- **경계 조건** 1개 이상 (빈 값, 0, 최댓값, 중복)
- **에러 경로** — `03-spec.md` 에러 처리 표의 각 행마다 1개

내부 구현이 아니라 **명세에 적힌 관찰 가능한 동작**을 테스트한다.
private 함수를 직접 부르는 테스트는 리팩터할 때마다 깨진다.

## 진행 보고

매 REQ 완료 시 한 줄로 보고한다:

```
REQ-003 완료 — 테스트 3개(정상/경계/에러) 통과, 전체 27 passed. 커밋 a1b2c3d
```

실패가 남아 있으면 숨기지 않는다. 몇 개가 왜 실패하는지 그대로 적는다.

## 막혔을 때

- **테스트를 어떻게 쓸지 모르겠다** → 명세가 모호하다는 신호다. 3단계로 돌아가 그 REQ를 다시 쓴다.
- **구현이 너무 커진다** → REQ가 너무 크다. REQ-003 을 003a / 003b 로 쪼개고 명세에 반영한다.
- **기존 테스트가 계속 깨진다** → 요구사항끼리 충돌한다. 구현으로 우회하지 말고 사용자에게 어느 쪽이 맞는지 묻는다.

## 마감

전 REQ가 초록불이면:
1. 전체 테스트를 마지막으로 한 번 돌려 **출력 그대로** 보고한다.
2. `04-traceability.md` 의 빈칸을 확인한다. 테스트 없는 REQ가 있으면 미완성이라고 말한다.
3. `02-goal.md` 의 DoD 를 실제로 확인한 것만 체크한다. 확인하지 않은 항목은 체크하지 않고 이유를 적는다.
